How to debug this

One clip, ten stages, and the number that decided each one.

The pipeline turns a video into a count, a score and a list of technique faults. When it gets one of those wrong, exactly one stage is responsible. Debugging is walking left to right until the numbers stop matching what you can see in the frame — and every stage below prints the value it measured and the threshold it compared it against, so you can check it instead of believing it.

The walk

Each stage consumes what the one before it produced. A wrong answer at stage 3 makes the later measurement stages confidently wrong, so always find the first stage whose output disagrees with the video.

The three terracotta stages are the ones that produce a confident wrong answer rather than an error. They are where to look first when nothing crashed but the result is nonsense. Every constant governing each stage →

Debug one video, start to finish

  1. Pick the video

    On the Library, click a card. Cards are one per video, not one per file — if the same clip sits in three folders you get one card and one history. Debug this → opens it in the inspector with its most recent run.

  2. Run it, or open a run that already exists

    Leave movement on auto for the first pass. Press ▶ Run. The analysis happens in a separate process — a pose backend can take the interpreter down with it, and a server that died with the backend cannot tell you the backend died. Cached pose is reused; tick Fresh pose only when you are testing the estimator itself, because it costs about a minute.

  3. Walk the rail until the numbers stop matching the frame

    Use step into next stage (or ] / [) to walk the treatments in order — probe → pose → classify → model → fusion → … → payload. ↻ walk it advances on a timer. The left rail lists every treatment this run produced; click one to jump. You are looking for the first stage whose output you can contradict by watching the video — after that, everything is downstream of a mistake.

  4. Read the rejection, not the verdict

    Every discarded rep candidate prints the value it measured and the threshold it failed. amplitude 0.11 < min_amplitude 0.15 is checkable; “no reps found” is not. If the value looks right and the threshold looks wrong, you have found a tuning problem; if the value looks wrong, the problem is upstream.

  5. Put the claim on the pixels

    Click the signal chart to seek. Use − frame / + frame (or the arrow keys) and 0.25× playback to land on the exact frame a rejection names. The skeleton overlay is the pose the pipeline actually measured — if it is on the wrong person or lagging the body, stage 2 is your answer and nothing below it matters.

  6. Change one thing and compare

    Force a movement, or re-run after a code change, then pick the earlier run in Compare runs. The diff is rendered through the same renderer as barra explain, so it shows what changed in the run, not in the formatting. A comparison says what moved; it does not say which one is right.

  7. Write down what you saw, and export it

    Your review is stored in this browser only — timestamps make it useful (“at 22.6–25.2s the athlete is walking, not repping”). Export debug bundle writes the trace, the payload, your note and the selected interval as one JSON file. Export before clearing browser storage.

Getting videos in

Three ways, one library. All of them key on the file’s content, so importing the same clip twice never makes a second card.

From this page

Add video in the header. Select one file or several. Anything already in the library is reported as a duplicate and discarded rather than copied in again — the reply names the id that already holds those frames.

Drop files in a folder

Put clips in data/videos/ (or leave them at the repository root, or in server/data/) and press Rescan disk. Unchanged files are not re-hashed, so a rescan of a settled library is instant.

From the command line

python tools/debugweb/library.py scan
python tools/debugweb/library.py add clip.mp4
python tools/debugweb/library.py list
python tools/debugweb/library.py set <id> movement=pull_up
python tools/debugweb/library.py rm <id>

The library lives in out/library.db (SQLite). Its key is the sha256 of the file, its video_copies table records every path those bytes were found at, and rm never touches out/traces/ — traces are evidence, and evidence outlives the file it was taken from.

Where the evidence lands

Every run through this tool writes three files under out/traces/, in the project’s own formats — so anything you debug here is replayable on the command line and diffable against a run from the real server.

FileWhat it isRead it with
<traceId>.jsonthe decision trace: every step, rejection and error, in order barra explain --replay
<traceId>.payload.jsonthe analyzer result — exactly what the phone would receive the inspector’s payload tab
<traceId>.pose.parquetthe keypoints supplied to that run the skeleton overlay, pinned to that run

Older traces predate the pose snapshot and fall back to the current clip cache; the overlay says so when it does. This tool runs the measurement core — not the upload transport, not the remote vision coach, not Android rendering.

Checking the tool itself

.venv/bin/python tools/debugweb/server.py            # http://127.0.0.1:8091
.venv/bin/python -m pytest tests/test_debugweb.py -q
.venv/bin/python tools/debugweb/browser_e2e.py       # real run, real browser

The server binds to 127.0.0.1 and serves local video files; there is nothing to deploy. Three rules it holds to: it never computes an answer — every number shown is read out of a trace or a payload the pipeline produced; runs happen in a subprocess; and its output is the project’s output.
